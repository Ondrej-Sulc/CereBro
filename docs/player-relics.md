# Personal relic inventory

Status: implemented locally on `feat/player-relic-inventory`; not deployed.

`/relics` offers All Relics and My Relics views through the page heading. Without a saved view preference, signed-in users with a game profile open My Relics. The personal view manages the active game profile's Battlecasts and Statcasts; the catalog stays free of owned markers and saved builds. Players can add from My Relics or the selected variant/build on a detail page. The shared editor supports consecutive additions, rarity selection, rank/signature changes, live prestige and confirmed removal. Filters cover name, class, type, attribute and rarity; sorting covers rarity/rank, prestige and name. Desktop/mobile navigation has one Relics entry. The old `/profile/relics` URL redirects to the explicit personal view.

Champions uses the same All Champions / My Roster heading navigation at `/champions`. See [collection navigation](collection-navigation.md) for remembered preferences, explicit links and filter isolation.

Manual additions open a searchable portrait grid with type/class filters and owned markers. Each Statcast family appears once, with icon-backed secondary attribute choices in the build editor. The editor uses class-colored artwork, rarity/rank buttons, signature shortcuts and a slider. Switching to an unowned variant preserves the selected build within its bounds; an owned variant loads its saved build. Mobile keeps the action buttons visible while the controls scroll.

## Ownership and progression

`PlayerRelic` records a profile ID, exact relic source ID, source rarity ID, rank and signature. The unique profile/relic/rarity key permits different rarities and Statcast variants without duplicates. A composite foreign key prevents mismatched rarity references. Deleting a profile cascades its inventory; deleting a referenced catalog rarity is restricted. Catalog retirement preserves the saved item but disables progression edits and hides stale prestige. Users can still remove retired items.

No rune levels are tracked. Like champion level, **all unlocked runes are assumed maxed for the selected rank**. Displayed prestige comes from the verified `GameRelicPrestige` table for the exact variant, rarity, rank and signature. Invalid or stale source bindings yield no rating, never an estimate.

Champion binding, rune choice management and alliance editing are outside this version.

## Top-30 prestige

My Relics combines Battlecasts and Statcasts in one descending prestige list, takes at most 30 owned items, and rounds the final average to the nearest integer, matching champion roster insights. Ties use owned-item ID for stable membership; different source variants and rarities remain distinct owned items. The Top 30 filter and numbered contribution labels use the entire inventory, independently of search/class/rarity filters.

Existing profiles default to recorded/manual prestige. The panel always previews the known-entry average, but it cannot replace the profile value until at least 30 items have valid source-bound prestige and the player explicitly confirms their highest 30 are included. An inventory with fewer than 30 is a collection preview only, even if that is the player's entire collection; automatic aggregation for smaller accounts is intentionally not enabled without a verified game rule. Thirty entries alone do not establish that a collection is complete.

Activation sets `Player.relicPrestigeFromInventory=true` and writes the top-30 result to `Player.relicPrestige`, adding the current stored champion prestige to update `summonerPrestige`. Champion prestige is not inferred from an incomplete champion collection here. If champion prestige is absent, the confirmation explains that the initial total contains only the relic contribution. Subsequent relic add/edit/remove operations update both totals and a `PrestigeLog` in the same transaction. A profile row lock shared by inventory, champion updates, manual changes and Discord screenshot imports prevents lost component updates. Unchanged totals do not create duplicate history entries.

Unknown/stale ratings anywhere in the owned inventory, or fewer than 30 valid items, pause automatic writes and preserve the last recorded totals. No unknown entry is silently discarded on the assumption it would fall below the cutoff. Catalog/curve imports do not bulk-rewrite player profiles; the panel detects a changed preview and offers a fresh confirmation, while the next eligible inventory edit recomputes normally. Disabling automation keeps the current numbers. A deliberate manual edit or validated screenshot import switches automation off and becomes authoritative until the player enables it again. The profile editor and import response explain this precedence.

`PUT /api/profile/relics` changes the preference, with the same authentication, active-profile, origin, size and private-cache checks as inventory writes. Activation requires `confirmedTop30=true` and a SHA-256 revision of the displayed inventory/build versions, ratings and stored prestige components. A stale revision returns 409 and refreshes the preview before another confirmation. No client-calculated prestige is accepted. Reads never mutate profile totals.

## Writes and privacy

### Screenshot import

My Relics offers **Import screenshots** alongside manual entry. Users can choose files or paste images with Ctrl/Cmd+V anywhere inside the import dialog. Paste uses the clipboard event, so it does not request permission to read clipboard contents. Text pastes are ignored. Both paths accept up to six PNG/JPEG/WebP screenshots per selection, validate file type/size before scanning, and process them sequentially. A synchronous operation guard prevents rapid pastes or repeated save clicks from starting duplicate requests. Each request is capped at 8 MiB before multipart parsing and 24 million decoded pixels. Google Vision is the same OCR provider as champion uploads. Its shared client now loads only Vision configuration, so web OCR does not require Discord bot tokens or spreadsheet/model-provider credentials. The deployed web service still needs `GOOGLE_CREDENTIALS_JSON` and any desired `GOOGLE_VISION_*` overrides.

`POST /api/profile/relics/screenshots` authenticates the active profile and checks request origin before OCR. It reserves one screenshot against the existing shared champion/relic allowance under an actor advisory lock, then updates the usage event with success/failure and detected-card count. Relic scans use `mode=relics`, leave `processedChampionCount=0`, and keep their detected count in metadata. Failed paid attempts consume usage. No inventory rows are written by scanning; images and OCR text are not persisted by this route. The browser keeps temporary local image URLs for card previews and revokes them on close.

Recognition anchors on the relic's name/rating plate, not the small bound-champion portrait or upgrade arrow. It uses star tips, awakening colors, class glyph colors and consistent main-frame evidence. Uncertain rarity/class stays unknown. Complete recognized cards are matched against all exact current, source-bound rank/signature curves; there is no nearest-rating match, interpolation, guessed rank or champion-specific override. Rounded ratings can collide: 6-star Ant-Man at 1,962 matches both R3/sig187 and R4/sig87. A single match is preselected for review; multiple matches require a choice. Statcast variants additionally use the two right-side attribute glyphs: primary above secondary. Their white shapes are compared against all 11 game-font templates before filtering by catalog or prestige, so attributes with the same tile color stay distinct. A primary/family contradiction blocks matching; uncertain icons remain explicit, with no automatic selection even if the remaining prestige candidates contain just one build. Missing matches, unreadable/unknown labels and clipped cards need manual entry or a clearer screenshot. Inference assumes max-level unlocked runes, just as the inventory's prestige model does; non-max runes may produce a missing or misleading match, so the matching help explains this assumption and users can inspect or change builds before saving.

The review starts with processed screenshot/card counts and separate totals for decisions, ready cards and unmatched cards. Decisions appear first, followed by unmatched cases and compact ready results. Rank/signature alternatives are one-click tiles; different Statcast variants and rarities remain separate labeled groups. A choice moves its card into the ready section, where Change reopens the alternatives. Leave out is reversible through the skipped section. Conflicting selected duplicates move back into decisions and block saving. Source-card counts remain distinct from the deduplicated relic count in the save footer. Original crops link to their screenshots, and existing builds that will be replaced remain visible. Clicking Save imports the selected builds directly, with no additional confirmation checkbox. `PUT /api/profile/relics/screenshots` imports only selected entries in one transaction, validates live rarity bounds and each selected build's exact expected rating against current source-bound curves, and checks the displayed inventory revision under the existing catalog/player locks. Source drift, stale inventory, invalid entries or conflicting duplicate builds abort the whole batch. Identical duplicates coalesce, unchanged existing rows retain their versions, and omitted relics are never removed. Automatic top-30 prestige updates once per successful batch if already enabled; scanning/importing inventory does not itself enable or disable that preference. This is distinct from importing a profile's aggregate prestige screenshot, which remains a deliberate manual override.

`/api/profile/relics` resolves the authenticated active profile on the server. Each mutation also supplies the profile that was displayed; a profile change rejects the stale form. Client-supplied item IDs are always scoped to that authenticated profile. The collection and API responses are private and never placed in the shared public catalog cache.

POST creates (never upserts); PATCH and DELETE use the last observed `updatedAt` for optimistic concurrency. A duplicate or stale edit returns a conflict instead of overwriting another tab. Strict schemas reject invalid integers, extra fields and malformed input. Current catalog rarity bounds are checked inside the catalog import advisory lock before add/update; preference changes and removals use the same lock before the player row lock. JSON content type and same-origin checks protect the cookie-authenticated mutation routes.

Collection queries exclude raw catalog/scaling definitions. The editor loads only the chosen relic's progression options on demand; signature/rank previews then run locally without further requests.

The origin check uses the trusted deployment proxy's public host/protocol rather than Next.js's internal bind URL. Both direct and proxied same-origin requests are covered, alongside cross-origin rejection.
